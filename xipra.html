Executive Summary

Xipra Technology is a full-stack corporate platform built on the Next.js App Router. It combines a public marketing website, a certificate-issuance & public-verification system with on-demand QR codes, a database-backed CMS for editable page content, and a role-based admin panel for managing every entity.

System Architecture

The platform is a single Next.js application with two rendering worlds: cached/ISR public pages and dynamic authenticated admin pages, both sharing a typed service layer over Prisma and Supabase.

        │  Next.js Edge Middleware  (auth gate:      │
        │  /admin/**, /api/admin/**)                 │
        └───────────┬───────────────────────────────┘
                    │

                   validation (Zod) · authz · audit

             (pg adapter)           (7 buckets)

                   ▼                      ▼
          Supabase PostgreSQL      + Nodemailer SMTP (pooled)

Request flow — public page

  1. Browser requests a public route (e.g. /products). Middleware matcher excludes it, so no auth runs.
  2. Next serves the prerendered ISR HTML from cache (revalidate = 1h). Data loaders are wrapped in unstable_cache — no DB round-trip on a cache hit.
  3. On admin edit, the write service calls revalidateTag, regenerating the affected page on next request.

Request flow — admin action

  1. Client component calls fetch('/api/admin/...').
  2. Middleware verifies the JWT cookie; unauthorized → 401 (API) or redirect (page).
  3. The route handler re-checks with requireAdmin() (defense-in-depth), validates the body with Zod, invokes a service, writes to Postgres/Storage, logs an audit entry, and returns the standard JSON envelope.

Authentication Flow

Stateless JWT sessions in an httpOnly cookie. Passwords are bcrypt-hashed (12 rounds). Tokens are HS256, 7-day expiry. Verified in two layers: edge middleware and per-handler requireAdmin.

Login sequence
sequenceDiagram
    participant U as Admin Browser
    participant L as /api/admin/auth/login
    participant S as auth.service
    participant DB as PostgreSQL
    U->>L: POST email + password
    L->>L: rate-limit 10/min (IP)
    L->>L: Zod validate
    L->>S: loginAdmin(input)
    S->>DB: find admin by email
    DB-->>S: admin record
    S->>S: bcrypt.compare(password, hash)
    alt valid
        S-->>L: sign JWT (HS256, 7d)
        L->>DB: audit "auth.login"
        L-->>U: 200 + Set-Cookie (httpOnly)
    else invalid
        L->>DB: audit "auth.login.failed"
        L-->>U: 401 Unauthorized
    end
Protected request gate
flowchart LR
    A[Request to /admin or /api/admin] --> B{Middleware: JWT cookie valid?}
    B -- no, page --> R[Redirect to /admin/login]
    B -- no, api --> J[401 JSON]
    B -- yes --> H[Route handler]
    H --> C{requireAdmin / requireRole}
    C -- fail --> E[401 / 403]
    C -- pass --> OK[Execute + audit]

Email System

Nodemailer with a pooled SMTP transport (max 3 connections, 100 messages/conn), built entirely from environment variables. If SMTP isn't configured, sending is skipped gracefully so forms still succeed.

Pipeline

  • Immediate response: forms persist, then email is sent via Next after() — the HTTP response flushes first.
  • Pooling: pool:true, reused TLS connections.
  • Retry: up to 3 attempts with backoff, only for transient errors (ETIMEDOUT, ECONNRESET, 4xx SMTP); permanent failures fail fast.
  • Never throws: a mail failure can't break a submission.
  • STARTTLS: secure toggled by SMTP_SECURE (port 587 STARTTLS default).

Strengths

Architecture. Clean layering — pages → typed services → Prisma/Storage. Consistent API envelope via withApiHandler with granular Prisma error mapping (no accidental 500s).
